# Resource Steward — مراقبة موارد Arena محليًا

أداة Python قياسية خفيفة في `/home/user/resource-steward`، مشغّلها `/home/user/bin/resource-steward`. **ليست إضافة أصلية لأدوات Arena، ولا اعتراضًا تلقائيًا لكل أمر**. خدمة المراقبة تعمل فقط ما دامت العملية والبيئة حيتين؛ إذا أُعيدت تهيئة sandbox يجب إعادة تشغيلها. يستعملها المساعد بوصفها فحصًا افتراضيًا قبل المهام الثقيلة، ويمكنه مراجعة قائمة رفع Google Drive.

## أوامر الاستخدام

```bash
/home/user/bin/resource-steward status     # حالة RAM ومرشحي اللقطة والإنذارات
/home/user/bin/resource-steward preflight  # 0: مسموح/تحذير، 3: توقف عن بدء عمل ثقيل
/home/user/bin/resource-steward audit      # تقدير حجم الملفات المرشحة للحفظ
/home/user/bin/resource-steward queue      # ملفات >=25 MB بانتظار مراجعة Drive
/home/user/bin/resource-steward daemon --interval 15  # خدمة مستمرة؛ ابدأها بأداة عمليات الخلفية
/home/user/bin/resource-steward run -- python3 your_analysis.py  # يحرس العملية التابعة فقط
```

**رموز الخروج:** `preflight=3` عند STOP؛ `run=124` عند بلوغ حد أمان أثناء التشغيل؛ `run=125` إذا تعذّرت المراقبة أثناء التشغيل؛ `run=126/127` عند تعذّر بدء الأمر أو عدم وجوده؛ و`daemon=4` إذا كان قفل خدمة أخرى نشطًا. عند استقبال `SIGHUP` أو `SIGINT` أو `SIGTERM` يمرر `run` الإشارة إلى مجموعة مهمته ويخرج بالقيمة 128 + رقم الإشارة. قد يعيد البرنامج التابع الأرقام نفسها؛ استخدم حقل `status` في مخرجات JSON للتمييز. راجع حالة المهمة ونقطة تقدمها ولا تكرر تحليلًا طويلًا دون التحقق من العملية السابقة.

## كيف يعمل

- يراقب `memory.current/max/events` و`MemAvailable`، وعدد الملفات المرشحة للّقطة وحجمها المنطقي، ومساحة القرص. تُحسب حدود cgroup الحالية وأسلافها **المرئية** حتى جذر `/sys/fs/cgroup`، ويُستخدم أصغر هامش معروف مع الذاكرة المتاحة للنظام. لا يمكن اكتشاف حدود أسلاف مخفية خارج مساحة أسماء cgroup. عند تحديد `--cgroup` بمسار مخصص خارج الجذر الافتراضي، يفحص المستوى المحدد فقط ما لم تحدد حدّ الأسلاف صراحة بالخيار العام `--cgroup-root`. تظل لقطة Arena **best-effort ~128 MB/10000 ملف**؛ الفحص تقديري ولا يثبت ما ستحفظه المنصة فعليًا.
- ينذر عند **80 MB** مرشحة للحفظ، ويرفض `run` جديدًا عند **100 MB** أو 9000 ملف؛ هذه ليست حدودًا رسمية. يرفض `preflight` العمل إذا كان هامش الذاكرة أقل من **384 MiB**، أو بلغ استخدام إحدى مجموعات cgroup المحدودة **80%**، أو تعذّر قياس الذاكرة. يحذر إذا قل الهامش عن **512 MiB** أو بلغ الاستخدام **70%**.
- بالنسبة إلى قرص جذر العمل، يحذر `preflight` عند بقاء أقل من **2 GiB**، ويرفض بدء المهمة إذا بقي أقل من **512 MiB** أو تعذّر قياس المساحة. يفحص `run` حد **512 MiB** أثناء المهمة أيضًا. هذه الحدود ثابتة ومحافظة، ولا تمنع امتلاء القرص المفاجئ بين عينتين.
- الخدمة تطلب مراجعة أي ملف مرشح للحفظ **أو** داخل مجلد staging الخاص بها (`/home/user/.cache/resource-steward/`) حجمه **25 MB أو أكثر**، وتضع مساره/حجمه/وقت تعديله في SQLite صغيرة؛ لا ترفع ولا تحذف ولا تنقل ملفات بنفسها. تعرض `new_alerts` للتنبيهات الجديدة و`cleared_alerts` عند زوالها، ويحتفظ سجل الأحداث بآخر 200 حدث. لا مفاتيح Drive محفوظة محليًا.
- `run` يحرس مجموعة العملية التي أنشأها فقط؛ يوقفها إذا بلغ استخدام أي cgroup محدود مقاس **80%**، أو قل هامش الذاكرة عن **256 MiB**، أو قل القرص عن **512 MiB**. إذا تعذّرت قراءة الذاكرة أو القرص أثناء المهمة يوقفها بدل تركها بلا مراقبة. يرسل إشارة مناسبة ويمنح المجموعة حتى ثلاث ثوانٍ للخروج قبل `SIGKILL`؛ وبعد خروج الأمر الرئيسي يوقف أبناءه الباقين في المجموعة نفسها بدل تركهم بلا مراقبة.
- لا يمكن اعتراض `SIGKILL` الموجّه للحارس أو ضمان تنظيف عملية انفصلت عن مجموعتها، كما أن أخذ العينات **لا يضمن منع OOM السريع**. قد يؤدي الإيقاف إلى فقدان تقدم غير محفوظ؛ يجب أن يدعم التحليل نقاط تقدّم مستقلة.
- تجنب `/tmp` للملفات الكبيرة؛ هو `tmpfs` في هذه البيئة. استعمل `/home/user/.cache/resource-steward/...` مؤقتًا على `ext4` مع علمك أن `.cache` **لا يُحفظ في لقطات Arena**. البيانات المهمة الصغيرة (الكود/الحالة/الفهرس) تُحفظ خارج المجلدات المستثناة.

## سير عمل Google Drive عند وجود المساعد

1. راجع `queue` والمسار والحجم والخصوصية؛ لا تقبل اسم ملف فقط لإثبات هوية المحتوى. احسب SHA-256 محليًا بالدفعات عند الحاجة.
2. ارفع عبر موصل Google Drive المتاح للمحادثة، وليس باعتماد محلي داخل daemon. إذا تجاوز الملف حد الرفع المباشر استعمل مسارًا قابلًا للاستئناف **بعد اختباره والتحقق منه**؛ لا ترسل ملفًا ضخمًا كـbase64 إلى المحادثة.
3. احصل على **ID حقيقي** من استجابة الرفع، وتحقق من `size` وبصمة الملف البعيد إن كانت متاحة. سجل النتيجة فقط بعد هذا التحقق:

```bash
/home/user/bin/resource-steward record-upload \
  --path /home/user/path/to/file.bin \
  --drive-id 'REAL_ID_FROM_CONNECTOR' --verified-bytes 12345678
```

`record-upload` **لا يتصل بـDrive ولا يتحقق بنفسه**: يطابق فقط حجم/زمن الملف المحلي مع حالة الطابور، ويثق بمعرّف Drive وحجمه البعيد اللذين يزوده بهما المشغّل. أي `--checksum` اختياري يُخزَّن كما هو؛ لا يحسب البرنامج بصمة الملف المحلي أو البعيد ولا يقارن بينهما. يتعين على المشغّل التحقق من نتيجة الرفع وهوية الملف البعيد وحجمه قبل التسجيل. **حالة قاعدة البيانات `verified` اسم قائم للتوافق، وتعني تسجيل تأكيد المشغّل، لا تحقق البرنامج من Drive.** لا تحذف ملفات المستخدم الأصلية تلقائيًا؛ حذف مؤقت أنشأته الأداة ممكن بعد تحقق الرفع. إذا تغيّر الملف، يُرفض التسجيل وتحتاج إلى طلب جديد.

يعرض نجاح `record-upload` قيمة `status: "verified"` (الاسم القائم) مع `verification_source: "operator"` و`remote_verified_by_tool: false`. **لم يتغير سلوك هذا الأمر؛ لا يزال يعتمد على تأكيد المشغّل.** أُضيف أمر منفصل اختياري `verify-drive-upload` يطلب `RESOURCE_STEWARD_DRIVE_TOKEN` من بيئة العملية؛ يستعلم عن بيانات ملف Drive الثنائي عبر API ويقارن الحجم وMD5 مع الملف المحلي قبل التسجيل. إذا نجح يعيد `verification_source: "remote_checksum_checked"` و`remote_verified_by_tool: true`. لا يخزّن الرمز ولا يرفع الملفات؛ MD5 يفحص سلامة النقل الاعتيادية لا يحمي من تصادم مقصود أو انتحال مزود الخدمة. ملفات Google Docs الأصلية التي لا توفر MD5 ثنائيًا تُرفض. لا تمنح الرمز إلا صلاحية القراءة اللازمة وتجنب طباعته أو وضعه في وسائط CLI أو المستودع:

```bash
export RESOURCE_STEWARD_DRIVE_TOKEN='ACCESS_TOKEN_FROM_YOUR_OWN_AUTH_FLOW'
/home/user/bin/resource-steward verify-drive-upload \
  --path /home/user/path/to/file.bin --drive-id 'ID_FROM_DRIVE'
unset RESOURCE_STEWARD_DRIVE_TOKEN
```

التحقق بالرمز هنا **تكامل اختياري مستقل عن موصل المحادثة**؛ لا يمكن للأداة الحصول تلقائيًا على رمز الموصل. تغيّر مخطط SQLite إلى الإصدار 2 لتمييز مصدر التحقق، مع ترحيل السجلات القديمة إلى `operator` مع الإبقاء على قيمة `status=verified` للتوافق.

**اختبار سحابي منفصل للنسخة المطوّرة (30 أكتوبر 2026):** أُنشئ ملف عشوائي غير شخصي حجمه **110,000,000 بايت**، ورُفع باستخدام جلسة رفع قابلة للاستئناف عبر موصل Google Drive في المحادثة، ثم نُزّل بالكامل من رابط مؤقت بعد موافقة المستخدم. تطابقت SHA-256 المحلية والمنزّلة: `8b79b77ea072759b11a7ab65b73b1c2ba10f7ac18d0f5e3abbd638fe4df6744a`؛ أظهر Drive الحجم نفسه وMD5 مطابقًا (`56f069d17dedb4a9b88a712977f8bc7d`). أُلغي الوصول العام المؤقت بعد الاختبار وتحققنا من بقاء صلاحية المالك فقط. لم نُضمّن معرّف الملف الخاص في التوثيق العام. هذا اختبار واحد لمسار المساعد/الموصل، **وليس اختبارًا لرفع أجرته الأداة أو ضمانًا عامًا لكل الملفات والشبكات**. اختبار الـ110 MB الأصلي في `tests` لا يزال اختبارًا محليًا بملف sparse.

## حالة SQLite والترقيات

يستخدم البرنامج `PRAGMA user_version = 2`؛ تُرقّى قواعد الإصدار 1 أو القواعد القديمة الكاملة غير المرقّمة (`user_version = 0`) داخل معاملة بإضافة `verification_source` دون حذف الطابور أو الأحداث أو التنبيهات. السجلات المسجّلة سابقًا بحالة `verified` تُنسب إلى `operator` لأنها لم تُفحص عن بُعد بواسطة الأداة. يرفض قاعدة بإصدار أحدث أو مخطط قديم غير مكتمل بدل استبداله بصمت. عند تعذّر فتح حالة معطوبة، يعرض CLI `storage_error` ويخرج بالرمز 5؛ لا يُصلح القاعدة تلقائيًا.

قبل أي ترقية مستقبلية تغيّر أعمدة الحالة، أوقف `daemon` وخذ نسخة احتياطية متسقة من SQLite (مثل `sqlite3.Connection.backup()`)، ثم اختبر الترقية على نسخة من بيانات حقيقية منزوعة الأسرار. ينبغي أن تكون ترقية المخطط التالية معاملة صريحة تحفظ السجلات وترفع `user_version` فقط بعد نجاح كل التغييرات. تستخدم عمليات تعديل الطابور وتأكيد التسجيل والتنبيهات معاملات كتابة تبدأ بـ`BEGIN IMMEDIATE` لتسلسل التحديثات المحلية؛ هذا لا يغني عن اختبارات تشغيل موسعة عبر عدة عمليات أو خطة للتعافي من تلف البيانات.

## التحليل الطويل

`run` لا يصنع checkpoints لبرنامج عشوائي؛ ينبغي تصميم التحليل نفسه في أجزاء ذات هوية ثابتة وحفظ التقدم في ملف صغير أو SQLite. يتضمن المستودع الآن مثالًا عمليًا في `examples/checkpointed_task.py`: ينشئ مخرجات حتمية لكل خطوة ويكتب مؤشر التقدم بشكل ذري؛ إذا توقف بعد كتابة مخرج وقبل تحديث المؤشر، تُعاد الخطوة بأمان. جرّبه من جذر المستودع:

```bash
python3 examples/checkpointed_task.py --workdir ./task-progress --steps 5 --interrupt-after 2
python3 examples/checkpointed_task.py --workdir ./task-progress --steps 5
# أو مرّر الأمر الثاني إلى resource-steward run -- بعد preflight
```

احفظ `task-progress` خارج `.cache` والمجلدات المستثناة إذا أردت استعادته في اللقطات؛ حذف مجلد التقدم أو تلفه يتطلب تدخّلًا ولا يُصلح تلقائيًا. تشغيل `run` نفسه **اختياري وباستدعاء صريح**؛ ليس إضافة Arena أصلية ولا يعترض أوامر أخرى. شغّل الأعمال الطويلة عبر أداة العمليات الخلفية عند الحاجة. أخذ العينات لا يمنع OOM السريع، أو `SIGKILL` الموجّه للحارس، أو عمليات تنفصل عن مجموعته؛ لذا لا يمكن ضمان حفظ كل تقدم.

## اختبارات وإيقاف

```bash
python3 -m unittest discover -s /home/user/resource-steward/tests -v
# استخدم أداة إيقاف العملية للخدمة التي بدأت بأداة عمليات الخلفية
```

الخدمة نفسها لا تشغّل خادم ويب أو تستمع على منفذ. لا حاجة لـnpm أو sudo أو swap؛ التثبيت محلي تحت `/home/user`. استخدم `--help` لمعرفة الخيارات.
